# Почему это MVP и что требуется для полной версии

**Архив состояния 0.1.** Значительная часть перечисленных ниже технических пробелов закрыта в версии 0.2.
Актуальное состояние и оставшиеся условия запуска: [RELEASE_02.md](RELEASE_02.md).

В предыдущей итерации реализованы архитектура, промпты и технический каркас. Полный объём концепции ещё
не реализован: это реальное ограничение результата, а не название тарифа и не ограничение Python/Railway.

| Область | Сейчас | Для полной версии |
|---|---|---|
| База мошенничества | 3 учебные draft-карточки | 150–300 проверенных карточек, 12 категорий, RU/KK/mixed, редактор |
| Законодательство | Таблица и фильтры, проверенных норм нет | Актуальные фрагменты с редакцией, датами действия, ответственным юристом |
| Поиск | Лексический PostgreSQL FTS | Многоязычный semantic + FTS, reranker, измерение recall на реальных формулировках |
| Правовые выводы | Проверяется структура и существование citation ID | Проверка соответствия каждого утверждения конкретному источнику и его применимости |
| Диалог после ущерба | Общая маршрутизация, история и вопросы | Типизированные анкеты А–Д, подтверждение фактов и переходов, отсутствие потери важных сведений |
| Документы | LLM-черновик TXT, плейсхолдеры | Утверждённые юристом шаблоны RU/KK, заполнение слотов, PDF/DOCX с визуальной проверкой |
| Файлы | Основные форматы, ограничения, image input | Скан-PDF/OCR, дополнительные форматы, безопасная конвертация, антивирус, изолированные parsers |
| Ссылки | Не открываются, маскируются | Безопасный URL-анализ с защитой SSRF/редиректов и понятными ограничениями |
| Надёжность | Один polling-процесс, RAM-сессии | Очередь, дедупликация, отмена, TTL, восстановление, лимиты нагрузки/затрат |
| Приватность | Согласие, частичное маскирование, /delete | Проверенная политика обработки, полный жизненный цикл удаления, защита логов и внешней передачи |
| Качество | 28 исходных тестов механизмов | Испытания реальных LLM-ответов на RU/KK, юридическая оценка, ложный low-risk, нагрузка |
| Операционная работа | Файлы конфигурации и инструкция | Мониторинг, оповещения, бэкапы/восстановление, обновление источников и отзыв ошибочных карточек |

## Порядок работ

1. **Подключить и проверить инфраструктуру.** Railway, PostgreSQL, токен Telegram, LLM, миграции,
   smoke-тест на синтетике, реальные время ответа и стоимость запроса.
2. **Сделать правовое ядро.** Собрать и проверить источники, первоначальные карточки, hybrid RAG,
   привязку выводов к источникам; по источникам честно выдавать «не подтверждено», если основания нет.
3. **Довести пользовательские сценарии.** Все ветки после происшествия, корректные уточнения,
   подтверждение OCR/сумм, утверждённые шаблоны, скачиваемые документы, консультация юриста.
4. **Довести обработку файлов и защиту.** OCR, нужные дополнительные форматы, parser sandbox,
   приватность, ограничение очереди и бюджета, корректный отказ на неподдерживаемое.
5. **Провести закрытый пилот.** Юрист и носитель казахского языка оценивают ответы; затем регрессии,
   нагрузка, восстановление и мониторинг. Публичный выпуск — после устранения критических ошибок.

Для пилота необязательно сразу 300 карточек, аудио/видео или веб-приложение. Обязательны качественные
источники для заявленных сценариев, отсутствие выдуманных правовых обещаний, рабочие документы,
защита данных и проверка поведения на реальной модели.

Большая модель помогает анализировать, но сама по себе не обеспечивает знание действующей редакции права РК,
качественный казахский, правильное применение нормы и достоверность цитат. Это свойства всего процесса.
Разработку инфраструктуры, поиска, анкет, документов и тестов можно выполнять программно; публикация
юридически проверенной базы требует содержательной проверки специалистом, а не автоматической метки reviewed.
